# HB–CS–CMS–SM: інтеграція прийнятої Visual 4

Користувач прийняв ділянку 04.11.2026. Це розподіл готової геометрії по файлах,
без переміщення опор, проводів, знаків або зміни електричних параметрів.
Усі **1867 об’єктів** збережено рівно один раз; **31 оригінальний файл** автора
залишається байт-у-байт незмінним. Після додавання маємо 40 scenery-файлів і
12936 об’єктів у сумарній мережі.

## Розстановки

Шлях у репозиторії: `unity_project/Assets/Catenary/Scenery/`.
Кожен новий JSON має `.meta` з постійним унікальним GUID та `assetBundleName: catenary`.

| Файл | Об’єктів | Вміст |
| --- | ---: | --- |
| `scenery_HB-CS[HB].json` | 386 | Вихід HB, нова діагональ трикутника та підхід до N09; HB1500. |
| `scenery_[HB]![CMS].json` | 33 | Знеструмлена нитка N09, її анкери та шість знаків. |
| `scenery_CS-HB[CMS].json` | 212 | Від N09 до південного підходу CS; CMS1500. |
| `scenery_CS.json` | 76 | Наскрізний маршрут CS, платформи та кріплення під переходом. |
| `scenery_CS-CMS.json` | 702 | Перегін від CS до вхідної горловини CMS; CMS1500. |
| `scenery_CMS.json` | 139 | Транзитна дуга CMS і єдина нова підстанція CMS1500. |
| `scenery_CMS-SM[CMS].json` | 94 | Вихід CMS до N04; CMS1500. |
| `scenery_[CMS]![SM].json` | 30 | Знеструмлена нитка N04, її анкери та шість знаків. |
| `scenery_SM-CMS[SM].json` | 195 | Від N04 до стику з авторською мережею біля кільця SM; SM1500. |

`[HB]`, `[CMS]`, `[SM]` позначають район живлення відповідної частини перегону;
`[A]![B]` — нейтральну нитку та її знаки, як у файлах автора. Розподіл по файлах
не створює нових анкерних стиків. Опора та використаний на ній анкер можуть
належати сусіднім файлам: вони завантажуються разом. CMS1500 визначена тільки
в `scenery_CMS.json`; HB1500 та SM1500 залишаються в авторських файлах.
Завантажувальна колія CMS не електрифікована.

## Перевірка вихідного проєкту

```powershell
python .\tools\verify_phase1_release.py
python .\tools\validate_project.py
python .\tools\test_authoring_tools.py
```

Перша команда звіряє контрольні суми файлів, кількість і всі значення об’єктів,
їхню кратність та відновлення початкового порядку Visual 4. За потреби прямого
порівняння з вихідним тестовим JSON:

```powershell
python .\tools\verify_phase1_release.py --accepted-scenery 'C:\path\scenery_phase1_hb_cs_cms_visual1.json'
```

Маніфест `audit/phase1_hb_cs_cms_sm.json` зберігає відповідність старого індексу
об’єкта новій парі файл/індекс. Він не є runtime-розстановкою.
Геометрія зафіксована: перевірка навмисно повідомить про будь-яку її зміну.

## Складання й повторний тест

1. Відкрий `unity_project` у Unity **2019.4.41f2**. Дочекайся імпорту нових JSON
   разом із їхніми `.meta`.
2. Виконай **Catenary → Export OCS**. Нові файли повинні потрапити до `catenary`;
   старий export receipt більше не відповідає набору ресурсів.
3. Збери проєкт штатним `BUILD.cmd` або `tools/Build.ps1`.
4. Закрий гру та збережи резервну копію встановленого мода.
5. Перед тестом нової збірки перенеси
   `Mods/Derail-Valley-Catenary-DC/Scenery/scenery_phase1_hb_cs_cms_visual1.json`
   у резервну папку **поза Scenery**. Інакше монолітна тестова версія продублює
   вбудовані дев’ять файлів і визначення CMS1500.
6. Встанови результат зі штатної папки `ready-to-install`. Використай новий
   `network.json`: профіль `hb-cs-cms-sm`, `included_scenery: null`.
   Для власного allowlist додай усі дев’ять назв із таблиці, прибери стару
   тестову назву й залиш файли авторських районів HB/SM та їхніх стиків.
7. Повтори проїзд у грі: трикутник HB і анкер на порталі, N09, платформи й
   перехід CS, транзит CMS, N04 та стик біля кільця SM. Для перевірки складання
   достатньо переконатися, що розстановка відповідає прийнятій Visual 4 та
   немає дублювання об’єктів або помилок завантаження підстанцій.

Налаштування нейтральних ділянок збережені: виміряні проміжки N09/N04 —
117/130 м, попередня оцінка передбачає до 80 м між електрично з’єднаними
пантографами. Нових нейтральних вставок або районів живлення не додано.

## Межі перевірки

Під час підготовки пройдено пряме порівняння з Visual 4, 65 перевірок проєкту
та 50 Python-тестів авторських інструментів. C#-тест обліку об’єктів оновлений
на 11069 + 1867. C#-тести, Unity export, Windows-складання і новий проїзд у грі
в цьому середовищі не виконувалися. Геометричні результати Visual 4 зберігають
силу через точну тотожність об’єктів; це не замінює тест нової збірки.
